# A node's skill choice is exactly its skills, and each client gets it its own way

A node's agent can use a choice of skills. The node's skill picker lists the skills that the node's client loads on this machine, and the person ticks the ones the agent may use. Claude Code and Pi are limited to exactly the chosen skills. Codex turns off the skills that were not chosen. Antigravity CLI's picker is off, with the note "Antigravity CLI uses all of its installed skills; it can't limit them per task." The owner decided this on 2026-10-09 in issue [#93](https://github.com/Mano-Liaoyan/iDevelop/issues/93). The same day the owner settled what a node starts with, what counts as installed, and what happens to a chosen skill that is no longer installed. On 2026-10-11 the owner decided that a task whose client's skill list can't be read at launch still runs. The [research note](../research/2026-10-09-client-sessions-and-skills.md#skills-by-client) records how each client finds and limits skills.

## How it works

- **No choice means every skill.** A node starts with no choice. Its agent then uses every skill its client loads, including skills installed later, and the picker shows every listed skill ticked. The first untick keeps exactly the skills still ticked. Unticking every skill means no skills. The Skills row's revert arrow clears the choice, so the node uses every skill again. Choosing another client clears the choice, because each client names and finds its skills its own way. Save as Blueprint keeps the choice, as it keeps the model.
- **The choice is part of the agent.** A task's `execution` in the workflow file, and a blueprint's default, gain an optional `skills` array of the client's own names. It is written sorted, and only when set, so a file without a choice keeps every byte and the format stays `idevelop.workflow/3`. An older build refuses a file that uses it, as it refuses a workflow's `name`. A run's revision and an attempt log name the skills only when set too, so every earlier revision keeps its id.
- **The client lists its own skills, without a model turn.** The client directory asks the client, the way it asks for models, but in the project folder, so the listing holds the person's own skills, the plugins enabled for the user or by the project's settings, the project's skills, and the client's built-in skills where its listing can tell them apart. A listing is kept for each client and folder until the client's next refresh. The first request after a refresh lists the skills again and keeps the last listing until the new one is in, so a start during a refresh, such as a run's next task, still has it.
  - Claude Code: `claude -p --input-format stream-json --output-format stream-json --verbose` with an `initialize` control request and then a `reload_skills` request. The `reload_skills` answer lists the session's skills alone, its bundled skills among them, which is the set the `initialize` allow-list chooses from. A Claude Code that cannot answer `reload_skills` falls back to the commands of the `initialize` answer. Those mark Claude Code's own rows, its built-in commands, such as `/compact`, and its bundled skills alike, so the fallback leaves them out, and the open picker says so in one line: "Claude Code doesn't list its built-in skills, so a choice leaves them out."
  - Codex: `codex app-server`, which iDevelop initializes before it sends `skills/list` with the project as its folder. The list holds every scope, including Codex's bundled system skills and the skills of its remote plugins, such as `pages:write-page`. A skill the person's configuration turned off is left out, because Codex does not load it. Codex 0.160.1 lists the remote plugins' skills only once it has loaded them in the background, about half a second to a second after the app-server starts, and nothing marks when (probe, 2026-10-11). So the listing asks again every 300 ms until at least 1.5 seconds have passed and two answers in a row agree, or until 8 seconds, and keeps the last answer. The owner decided on 2026-10-11 that a choice turns those skills off too, by the name the list gives, which the probe confirmed works.
  - Pi: `pi --mode rpc --no-session` with `get_commands`. The listing keeps the entries whose source is a skill, by the name after `skill:`, with the file each one loads from. Pi 1.1.0 loads a project's own skills, in `.pi/skills` and in each `.agents/skills` from the folder up, only once the person trusted the folder in Pi, so the listing holds exactly what Pi loads. The owner decided on 2026-10-11 that the picker keeps it that way and, while the folder isn't trusted, says under the open list: "This project's skills appear after the folder is trusted in Pi." iDevelop tells that without a model turn, as Pi does: the nearest folder that `trust.json` in Pi's agent folder (`PI_CODING_AGENT_DIR`, or `~/.pi/agent`) names, then the `defaultProjectTrust` setting. It reads those files and never writes them. A Pi extension can also decide trust, which only Pi itself can tell.
  - Antigravity CLI: none, because it has no per-run control.
- **Only what needs the listing asks for it.** The picker asks when it opens and while the node has a choice, whose missing skills it names. A start asks only for a node with a choice. Each turn of a run uses the project folder's listing, the one the person chose from.
- **Every turn passes the choice.** A client's resume does not keep it, so each turn's launch carries it:
  - Claude Code gets the chosen names as the `skills` allow-list of the `initialize` request that iDevelop already sends.
  - Pi gets `--no-skills` and `--skill <file>` for each chosen skill.
  - Codex gets `skills.config` in the `config` of `thread/start` or `thread/resume`, with `enabled = false` for each listed skill that the node did not choose.
  - Antigravity CLI gets nothing.
- **A chosen skill that is no longer installed is skipped.** The turn runs with the chosen skills the client still lists. The Skills row names the missing ones, for example "gone is not installed, so the task runs without it.", and the attempt's activity says "Claude Code runs without gone, which is not installed." The picker keeps a missing skill ticked as "gone (not installed)", so the person can see it and untick it. Pi gets only the files that exist.
- **A start with a choice waits for its listing while it runs.** While the client lists its skills, the start says "iDevelop is still listing the skills Claude Code loads, which this task's choice needs."
- **A skill list that can't be read does not stop the task.** The owner decided on 2026-10-11 that the task runs anyway and a note says so. Claude Code gets the chosen names as its allow-list, unchecked. Codex can only turn off the skills that were not chosen, and Pi loads a chosen skill only from its file, and both come from the list, so for them the choice can't be applied and they run with all of their skills. The owner confirmed that behavior the same day. The Skills row and the attempt's activity say which, for example "Codex's skill list couldn't be read, so the skill choice couldn't be applied, and Codex runs with all of its skills." The activity adds the reason. The open list says why the list failed and that checking the agents again lists the skills once more.

## Considered options

- **Reading the skill folders directly.** It would miss plugins enabled by settings and the bundled skills, and copy each client's own discovery rules into iDevelop, where each client's next release could change them.
- **Codex's `-c skills.config=[...]` on the command line.** It is the same session overrides as the thread's `config`, but its TOML array cannot pass an npm `codex.cmd` shim on Windows, so iDevelop would refuse to start the task. The thread's `config` is JSON on stdin.
- **Refusing a start whose chosen skill is not installed,** as a model that the machine does not offer refuses it. The owner chose to skip the skill and run.
- **Refusing a start whose client's skill list can't be read,** because Codex and Pi then cannot be limited. The owner chose on 2026-10-11 to run and say so.
- **Claude Code's `initialize` commands alone.** They mark the built-in commands and the bundled skills alike, so the picker could not offer a bundled skill, and any choice would drop every one of them. The owner asked for the built-in skills wherever a client lists them without a model turn, which `reload_skills` does. The `initialize` commands stay only as the fallback.
- **Listing Claude Code's own `initialize` rows anyway.** They mix built-in commands, which the allow-list does not govern, with its bundled skills.

## Consequences

- A skill installed after the person made a choice is not used until they tick it.
- A real-client probe that the owner approved on 2026-10-11 confirmed on Linux, with Claude Code 2.1.296, Codex 0.160.1, and Pi 1.1.0, that each listing runs no model turn, that Claude Code's allow-list and Pi's `--no-skills --skill` hold on every resumed turn, each turn with its own choice, and that Codex turns off each named skill on `thread/start` and `thread/resume`. Each client ignores a chosen name or file that matches nothing, without an error.
- Claude Code's allow-list is "exactly the chosen skills" for the main session only. A subagent takes its skills from its own `AgentDefinition.skills` and, in the follow-up probe, saw and ran every skill, bundled ones included. The owner decided on 2026-10-11 to keep that, and the Claude Code picker says under its list: "Claude Code's subagents can still use every skill."
- The allow-list matches a skill's full name or a `:name` suffix of it, as the 2.1.296 schema says and the follow-up probe confirmed. Choosing `probe-alpha` also lets in a plugin's `probeplug:probe-alpha`, and choosing the bundled `code-review` also lets in the plugin skill `code-review:code-review`.
- A listing starts the client in the project folder, so whatever the client does on starting there may run for a listing too. Claude Code runs the person's SessionStart hooks, and each listing leaves an empty `~/.claude/session-env/<session>/` folder, as each turn does.
- On Windows, Pi is an npm `pi.cmd` shim, and cmd.exe could misread a skill file's path with a space, such as one under `C:\Users\John Smith`. A launch with such an argument runs the node script that the shim runs, with the node.exe beside it or else the node on the search path, so node reads each argument as given. Every other launch still goes through the shim. A batch file that iDevelop cannot read as an npm shim still refuses the start and says that cmd.exe could misread the path. No Windows run has checked this yet.

Source: issue [#93](https://github.com/Mano-Liaoyan/iDevelop/issues/93), the owner's decisions of 2026-10-09 and 2026-10-11, and the real-client probes of 2026-10-11.
