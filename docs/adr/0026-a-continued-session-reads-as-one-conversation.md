# A continued session reads as one conversation

Each message starts a client process that resumes the node's own client session by its id, and no client process stays up between messages. The conversation view reads the turns that go on with one session as one conversation, with no New attempt marker between them. Pi cannot continue a conversation after the project folder moved, so iDevelop refuses that message with a note. The owner decided this on 2026-10-09 in issue [#92](https://github.com/Mano-Liaoyan/iDevelop/issues/92): keep resuming the same session for each message, with no long-lived idle client processes, and show a continued session as one conversation, with no "New attempt" divider when the session is the same. On 2026-10-11 the owner decided the Pi case in the same issue: refuse the message, with a note that Pi can't continue this conversation after the folder moved and a new conversation is needed, with no fork and no empty session under the same id. The [client sessions research](../research/2026-10-09-client-sessions-and-skills.md#probe-results-2026-10-09) holds the probe that found Claude Code, Codex, and Antigravity CLI resuming the same session in a new process, and Pi doing so in the session's own folder.

## How it works

- **A message resumes the session in a new process.** A person's message and a feedback edge's findings or note are the next turn of the node's session, which resumes it with the message alone ([ADR 0042](0042-execution-v2-a-node-is-an-agent-and-the-engine-only-routes-results.md)). A Retry and an upstream change start a new attempt in a fresh session.
- **A turn knows whether it went on with the session.** For a turn that resumes a session, the node's log says so once the turn's client reports the session it runs: the same id means it resumed it. A client that reports another session, or a turn that ends without reporting one, means the session started over. So does a Pi turn that printed Pi's notice "No project session found with id" on stderr, because Pi then reports the id it was given over an empty session. iDevelop checks each stderr line as it reads it, because a chatty client can push the notice out of the stderr tail that the exit event keeps, and the exit event records `lostSession`.
- **The view reads one conversation.** The turns of one session read as one conversation. When a turn runs another model, reasoning level, or conversation mode than the turn before, a Settings changed marker with its settings sits between them. A turn whose session started over shows a New attempt marker, and so does the first turn of each attempt.
- **Start a new conversation.** When a node's conversation cannot continue, because Pi's folder moved or the client reported no session, the refusal note in the conversation view and in the inspector offers Start a new conversation. After the person chooses it, the composer says "Your next message starts a new conversation." The next message then starts a fresh session. Its first prompt is the node's own prompt, exactly as when the node starts, followed by the person's message, and the view shows iDevelop's prompt, then the person's message. The owner decided all of this on 2026-10-11.
- **The inspector's list matches.** In the inspector's Talk to the Agent list, an attempt shows its status line only when it started a new session, failed, was interrupted, or was stopped, so a continued session reads as one list there too. The owner decided this on 2026-10-11.
- **A turn records its folder.** Each turn's entry in the node's log carries `workingFolder`, the folder the turn's client runs in, and the session's folder is the working folder of the turn whose client last reported the session.
- **Pi refuses a conversation whose folder moved.** Pi finds a session only in the folder where it ran. When a message would resume a Pi session from another folder than the session's, because the project folder moved or was renamed since the session's last turn, the start check refuses it with the note "Pi can't continue this conversation after the project folder moved, so it needs a new conversation." Nothing launches. Open in terminal is disabled for such a conversation with the same note, because Pi's own command would open an empty session there too. Folders compare by their full paths, without case on Windows and macOS, whose file systems usually ignore it, and with case on Linux. Claude Code, Codex, and Antigravity CLI find a session by its id from any folder, so they resume it from anywhere.

## Considered options

- One live client process per conversation, taking each message on its open input. The owner decided against long-lived idle client processes, which would hold a process while a node waits.
- Drop the marker in the desktop alone. Both conversation views read the history that Core projects, so the rule lives where the history is read.
- For Pi after a move, `--fork <id>`, which copies the history into a new session with a new id. The owner ruled out a fork. `--session-dir` does not find a session that ran in another folder, and `--session <file>` resumes the session but works in its old folder.

## Consequences

- A client that answers a resume with another session, or loses it, still shows a New attempt marker, so the person sees that the conversation started over.
