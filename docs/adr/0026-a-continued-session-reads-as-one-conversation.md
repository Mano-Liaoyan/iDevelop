# A continued session reads as one conversation

Each message still starts a client process that resumes the task's own client session by its id, and no client process stays up between messages. The conversation view reads the attempts that go on with one session as one conversation, with no New attempt marker between them. Pi cannot continue a conversation after the project folder moved, so iDevelop refuses that message with a note. The owner decided this on 2026-10-09 in issue [#92](https://github.com/Mano-Liaoyan/iDevelop/issues/92): keep resuming the same session for each message, with no long-lived idle client processes, and show a continued session as one conversation, with no "New attempt" divider when the session is the same. On 2026-10-11 the owner decided the Pi case in the same issue: refuse the message, with a note that Pi can't continue this conversation after the folder moved and a new conversation is needed, with no fork and no empty session under the same id. The [client sessions research](../research/2026-10-09-client-sessions-and-skills.md#probe-results-2026-10-09) holds the probe that found Claude Code, Codex, and Antigravity CLI resuming the same session in a new process, and Pi doing so in the session's own folder.

## How it works

- **A message resumes the session in a new process, as before.** A message to a task that is not running starts a new attempt whose first turn resumes the latest attempt's session with the message alone. A reply to a waiting attempt is the next turn of the same attempt. In a run, Continue fix and a review's fix rounds start a new attempt that resumes the earlier attempt's session. The launches do not change.
- **An attempt knows whether it went on with the session.** For an attempt that resumes another's session, the attempt's record says so once its first turn's client reports the session it runs: the same id means it resumed it. A client that reports another session, or a first turn that ends without reporting one, means the attempt started over. So does a Pi first turn whose stderr carries Pi's notice "No project session found with id", because Pi then reports the id it was given over an empty session. The reducer reads this from the events every log already has, so an older log folds the same way.
- **The view reads one conversation.** A conversation is a chain of attempts, each resuming the one before. An attempt that resumed the earlier attempt's session goes on with its conversation, and its New attempt marker goes. When it runs another model, reasoning level, or conversation mode than the earlier attempt last ran, a Settings changed marker with its settings takes the marker's place. An attempt that started over keeps its New attempt marker, and so does the first attempt of a chain. While the first turn starts, the attempt reads as going on. This holds for a task's own conversation and for a run's.
- **The inspector's list matches.** In the inspector's Talk to the Agent list of several attempts, an attempt shows its status line only when it started a new session or failed, so a continued session reads as one list there too. The owner decided this on 2026-10-11.
- **The attempts stay apart.** Each attempt keeps its own log, its place in the run journal, its lock, and its entry in the attempt picker. Picking an earlier attempt shows the conversation up to it.
- **An attempt records its folders.** The `requested` and `turnRequested` events carry `workingFolder`, the folder the turn's client runs in: the project for a task's own attempts, and the task's checkout `.worktrees/<run>/<task>` in a run. The attempt's record keeps the folder its session lives in: the working folder of the turn whose client last reported the session, or, until the client reports, the folder of the session it resumes, which a new attempt records as `continues.folder`.
- **Pi refuses a conversation whose folder moved.** Pi finds a session only in the folder where it ran. When a message would resume a Pi session from another folder than the session's, because the project folder moved or was renamed since the session's last turn, the start check refuses it with the note "Pi can't continue this conversation after the project folder moved, so it needs a new conversation. Run the task again to start one." Nothing launches, and the attempt stays as it was. The check covers a message to a task that is not running, a reply to a waiting attempt, a fix round, and a run's Continue and replies. Folders compare by their full paths, without case on Windows and macOS, whose file systems usually ignore it, and with case on Linux. Claude Code, Codex, and Antigravity CLI find a session by its id from any folder, so they resume it as before.

## Considered options

- One live client process per conversation, taking each message on its open input. The owner decided against long-lived idle client processes, which would hold a process, the task's lock, and the run's client slot while a node waits.
- A message to a task that is not running goes on as the next turn of the latest attempt instead of a new attempt. It would change the settled attempt's record, its lock, and the run journal's rules for a settled attempt, while the owner's decision names what the view shows.
- Drop the marker in the desktop alone. Both conversation views and the attempt picker read the history that Core projects, so the rule lives where the chain is read.
- For Pi after a move, `--fork <id>`, which copies the history into a new session with a new id. The owner ruled out a fork. `--session-dir` does not find a session that ran in another folder, and `--session <file>` resumes the session but works in its old folder.

## Consequences

- A client that answers a resume with another session, or loses it, still shows a New attempt marker, so the person sees that the conversation started over.
- A task's own attempts all run in the project folder, and a run's attempts of a task all run in that task's checkout, so a Pi message is refused only after the project folder moved or was renamed.
- An attempt logged before folders has no session folder, so a message that continues it resumes the session as before. If the project moved before then, Pi still opens an empty session under the same id, and its notice on stderr keeps the New attempt marker, so the person sees that the conversation started over.
- An older build reads a task's own attempt logs and ignores the folders, but refuses a run's attempt log that has them, as it refuses every newer field there.
