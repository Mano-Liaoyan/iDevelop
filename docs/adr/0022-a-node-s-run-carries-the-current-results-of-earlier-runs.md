# A node's run carries the current results of earlier runs

A node's run counts a task's result from an earlier run as complete while it is still current, so the tasks after the node start once all of their predecessors are complete, wherever their results came from. The run carries each such result into its own journal, its code replayed onto the run's base. A result whose code conflicts with that base is not carried, and its task must run again. Run Workflow still runs every task and carries nothing. The owner decided this on 2026-10-09 in issue [#90](https://github.com/Mano-Liaoyan/iDevelop/issues/90): with `A → C ← B`, when B succeeded in an earlier run and the person runs A, C starts once A finishes; when the project's code changed since B ran, B still counts if its changes apply cleanly on today's code, and on a conflict B must run again.

## How it works

- **A result from an earlier run counts as complete** when all of these hold. It was the current, non-stale result of its run, and that run showed the task as done: no later attempt replaced it and no block holds it. The newest settled run that ran the task is the one that decides, so a later run in which the task failed or was stopped leaves it no result: with `A → C ← B`, when B succeeded on Monday and a run on Tuesday ran B again and B failed, C waits for B on Wednesday. The coordinator decided this on 2026-10-09, because the card shows B as failed, and the owner judges by what the card shows. The task's definition, as the run approves it, and the connections into it are unchanged. Each result it took counts by the same rule, and is still its producer's result. `RunHistory` judges this from the workflow's settled E3 runs, in the order they were approved; a run that is still active does not count yet.
- **The approval carries what the node's run needs.** The run needs a result of each dependency predecessor of the tasks it may start that it does not start itself. For each such predecessor with a current result, `Carrying` builds a result with the origin `Carried(run, result)`, after a carried result for each result that one took. Its inputs are what the run's own materialization would build from the carried results, and its report and artifacts are the earlier result's. Its code is replayed onto those inputs the way Review updated inputs replays a stale result ([ADR 0009](0009-a-stale-result-is-rebased-as-one-merge-tree-commit.md)): one `git merge-tree` with the earlier result's input code as the merge base, as one commit whose parent is the new input code, with a frozen recipe. A result whose base did not move keeps its commit, and one that forwards code forwards the carried code. A carried task that took code from several tasks gets a join of the carried results, built the way a run's own join is: one source after another, from the merge base Git finds in their history, so two results that both took X's merge from X's.
- **The approval keeps them before the journal names them.** After the base pin of [ADR 0006](0006-run-approval-records-an-intent-and-pins-its-base.md), the approval builds the carried results again on the chosen base, keeps each new commit under `refs/idp/carried/<run-id>/<result-id>/code` or `/join`, and copies each artifact into the run's folder, checked by its digest. Then `Approved` records them as `carried`. The journal accepts a carried result only for a run that a node's Run started, only for a task that the run cannot start and has nothing of, only after every result it took, only with the ids its event derives, and only with the inputs, code, and artifacts the run's own materialization would build. Inside the approval's transaction, each must still be its task's current result in the history of every run read there. `carried` is never a run key, because run keys are hexadecimal, so no ownership snapshot reads these refs. A crash before the journal leaves the intent, and the next confirmation of the same content rebuilds the same commits and finds them kept. An intent that a confirmation of other content replaces takes its carried refs and copied artifacts with it.
- **A node run while a run is active carries the same way.** When the person's Run adds a node to the active run, the `requested` event carries the results that the tasks it adds need, kept and copied first in the same way, and a request the journal refuses lets go of what it kept, so `A → C ← B` works with B from an earlier run and A added to a run of another node. A repeat finds the request recorded. A task that the run already has a result of, such as one it carried, cannot be requested.
- **A conflict means the task must run again.** A result whose code conflicts with the run's base, or whose inputs do not join on it, is not carried. Neither is one that took a result of a task the run runs again. The tasks after it wait for it in the run, and a node whose own predecessor cannot be carried starts nothing: `Runs after "B". Run "B" first.` A read-only report has no code of its own, so it is carried under the other conditions.
- **The preflight lists what the run carries.** A node's preflight builds the carried results on each base it offers, as commits that nothing references, on HEAD and on a commit of the snapshot it would take, so it merges as the approval will. It lists each one: `Uses "B"'s result from an earlier run.` It says why it cannot use one on the chosen base, as in `Can't use "B"'s result from an earlier run: its code conflicts with this base in out-b.txt. The tasks after it wait until it runs again.` The run bar counts the tasks a node's run ran apart from those it carried, as in `2 of 2 done · 1 from an earlier run`. A base on which the node's own predecessors are not all carried cannot be chosen. A confirmation whose carried results differ from the live preview's is a changed preview.
- **In the run, a carried result is an ordinary result.** Its task shows as done, its inspector says that the run uses its result from an earlier run, it hands on to its dependents through the run's own materialization, and a consumer's claim checks no checkout for it, because it has none in the run, only its kept commit.
- **The cards keep each task's state between runs.** The canvas reads the workflow's runs when the project opens and when a run it shows settles, and judges them against the workflow as it is now. A task whose result counts shows `Succeeded`. One whose result no longer counts shows `Out of date`, in the state warning color with a sync glyph on its card and in its inspector, and says why once: `Out of date because it changed since it ran.`, or, when the task it took a result from is out of date too, under Run: `Out of date because "B" changed. Run "B" first.` when B changed itself, and `Out of date because "B" is out of date. Run "B" first.` when a task before B put B out of date, and when a later run of that task left it no result: `Out of date because a later run of "B" ended without a result. Run "B" first.` A task that its newest run could start and did not shows `Waits for "B"`, naming the predecessors that had no result in that run and have none since, or `Waits for 1 task` when the name does not fit the card whole, with the names in the card's tooltip, and Run says `Runs after "B". Run "B" first.` A task whose newest run that ran it ended without a result keeps how that run showed it, after the run and after a restart: `Failed`, `Cancelled`, `Closed as stopped`, or `Blocked`, with that run's detail and `A run of the "W" workflow ran this task last.`, unless a newer run held it without starting it, which `Waits for` then says. A settled run still on the cards keeps what it says of a task it ran until an edit puts that task's result out of date. A node's Run counts an earlier current result as complete before any click, so `Runs after "A". Run "A" first.` names only predecessors without one. The inspector offers a run's conversation only while the active run holds the task, or the settled one on the canvas started it, and neither carried it; otherwise Open conversation opens the task's own conversation. Every card follows one rule for the line under its title: its client while nothing about its task needs saying, that is while neither a run nor where it stands between runs says more than that it has not started, and its status otherwise.

## Considered options

- Count only results of the active run. The owner decided against it on 2026-10-09: a result from an earlier run counts while it is still current.
- Carry a result without replaying its code, and let the consumer's join merge it. A conflict would then block the consumer instead of saying that the earlier task must run again, as the owner decided.
- Replay each carried result from its own run's base, instead of from its input code. The replayed commits would not descend from the carried inputs, and the replay would differ from Review updated inputs.
- Keep the carried commits under the new run's own `refs/idp/<run-key>/` namespace. The run key is allocated only at the run's first preparation, after the approval names the commits, and a ref there would need a journaled move for the run's ownership check.
- Show "Waits for" on every task whose predecessors lack results. A workflow that never ran would show it on every card after its roots.

## Consequences

- A task whose newest run failed or was stopped has no result that counts, even when an older run left it one, so the tasks after it wait for it, as its card says.
- The title is part of a task's definition, so renaming a task puts its result out of date.
- A result whose code conflicts with today's code still shows `Succeeded` on its card until a node's preflight tries to carry it; the preflight says it cannot use it, and the tasks after it wait for it.
- An older build refuses a journal whose approval or request carries results, because it reads `carried` as an unknown field.
- The refs under `refs/idp/carried/` are never removed, as result refs are not: a run keeps one for each carried code result and each carried join, so they grow with the runs, which is bounded and accepted.
