# Dependency results

## Task

E2 is the slice "Materialize dependency results" of the [approved execution plan](2026-10-06-workspace-execution-plan.md#approved-delivery-slices). Its completion condition is that reports and artifacts reach successors, isolated code inputs produce a named revision, and fan-in conflicts and uncertain ownership block without corrupting work. Review fixes must use the correct code owner. It builds on the [D0 Git contract](2026-10-06-d0-design-validation.md) and the [E1 run journal](2026-10-07-run-and-input-records.md).

E2 ships as two pull requests. Pull request [#41](https://github.com/Mano-Liaoyan/iDevelop/pull/41) is E2a, based on E1's branch `feat/e1-run-records`. It adds `Materializer` and a Git adapter to `IDevelop.Core`. It adds no UI, no scheduler, and no launch path. E3 is its first caller. Pull request [#44](https://github.com/Mano-Liaoyan/iDevelop/pull/44) is E2b, rebased onto `main` after E2a merged. It adds `MergeJoins`, the real join composer, and the diamond suite.

A fresh Opus backend review of the coordinator's design note made twelve findings. The revised note accepted eleven and partly accepted one. GPT-6.1 Sol wrote the code through Codex. A GPT-6 Astra difficult-task review and an Opus backend review reviewed the code in seven rounds. The coordinator reviewed and amended every diff.

## Decisions and reasons

### E2 splits into E2a and E2b at the join composer

E2a owns the whole data contract. That covers the Git adapter, ownership keys, worktrees, result capture and publication, linear inputs, reports, artifacts, review-fix ownership, and salvage. A successor can consume one distinct accepted code revision. Two or more distinct code revisions block as `JoinRequired`.

E2b adds clean joins, durable conflict blocking, and the real-Git diamond suite. It passes a real `IJoinComposer` to `Materializer.Open`. It edits E2a in three places. `GitRepository` becomes `partial`, so that the merge code lives in a new file and still runs through the adapter's forced Git settings. `ConflictEvidence` gains `AttributeSource`. The general Git floor stays at 2.39, and a join needs Git 2.43. The composer receives a `JoinRequest` with the workflow, run, task, allocated input ID, frozen sources, and the expected previous join. It must use E2a's Git adapter, repository mutation lock, commit recipes, and `RefPublisher` for every ref move. E2a then checks the returned join's persisted receipt, complete source set, object type, tree, ordered parents, and ref transition before it accepts the input. E2b must also prove that the tree is the clean merge of those sources. `JoinRequest`, the `Join` plan case, join verification, `WriteEvidence`, and `ConflictEvidence` are in E2a, and fake composers test that boundary.

The Opus design review asked for the split. It keeps the contract in one owner's hands and gives E2b a boundary it can test without editing E2a.

### Code selection is a sum type

An input's code is `Root` (the approved run base), `Single` (one accepted revision), or `Joined` (a join of at least two). A writer result carries `Produced` code with its owner, attempt base, commit, tree, and result ref. Read-only and review results carry `Forwarded` code and never become owners. `CodeSource.Owners` lists every writer owner, so a reviewer that forwards a join owns none of them. The input's code base is computed from the selection, so a caller can no longer supply it. `RunStore.Plan` freezes bindings and sources, and `Reserve` derives the input record from the plan.

New runs write schema 2. Schema-1 journals decode `codeBase` as a `Legacy` selection and re-encode byte for byte. Inventing `Root` provenance for that history was rejected.

### Each run ref has one journaled expected state

This invariant governs every ref and HEAD change that E2a makes:

- iDevelop moves the refs it owns only through `RefPublisher`, a journaled compare-and-swap. `RefPublisher` checks the live ref against the journal before it records an intent.
- `RefOwnership.Accepts` folds the journal in order into one expected state per run ref. An observation makes the state exact. A pending compare-and-swap allows its old or its new value. An editable writer's preparation opens a lease that allows descendant commits until the next observation of that branch. Retained salvage makes the recorded branch tip exact when that tip equals the expected value or a pending target, or when the branch holds a lease. Under a lease, salvage adopts any tip, including a rewind below the attempt base. Publication then blocks, because the branch tip must contain the attempt base. No older entry can excuse a value. Any other state blocks as `UncertainOwnership`.
- `reset --hard`, HEAD attach, and path removal run only after a live check that HEAD is the task branch and the branch is at its expected value.
- No branch moves away from a commit unless a retained ref keeps that commit reachable.

The lease is the one place where the journal records permission rather than an exact value. Without it, two overlapping sibling writers could not both publish, which the diamond rule requires. Readers and reviewers never hold a lease.

### The invariant replaced inference from history

The first two review rounds fixed findings one at a time, and each round failed the same gate. Each fix assumed that a ref or HEAD state was legitimate if any journal entry in the run's history, or any Git ancestry relation, could have produced it. `ExplainedRef` accepted any value that an old intent had targeted. `SiblingFastForward` accepted any descendant of a sibling's last known commit, even after the sibling could no longer write. Retry skipped a journaled attach and then ran `reset --hard` against whatever HEAD named.

Round 3 took a census before writing another fix. `CensusTests.cs` replays every reproduction from the earlier reviews plus added counterexamples, and tags each run with the mechanism that decided it. At `0f4a189`, 15 of 39 runs failed. Every failure was an excuse from an older journal entry, from Git ancestry, from snapshot equality or a matching target, from a journal assumed to describe live HEAD, or from a branch moved without retention. One more failure compared index bytes instead of index content. All 11 runs where E2a checked live state before mutating passed. GPT-6 Astra agreed to change the invariant rather than narrow the exceptions, because no failure sat in a live check. `ExplainedRef`, `SiblingFastForward`, the own-branch ancestry rule, and target adoption without an intent were deleted. Rounds 4 and 5 applied the same invariant to older code paths that it did not yet cover, and the census grew to cover them.

### Worktrees and branches have fixed names and a recorded lifecycle

Keys are the first eight hexadecimal characters of SHA-256 over the full lowercase ID, lengthened only on collision. Workflow execution requires the project folder to be Git's worktree toplevel and Git 2.39 or later, so Apple's Git 2.39.5 runs single-input tasks. A join needs Git 2.43 or later. On an older Git, a join blocks as `GitVersionUnsupported` before any Git work, with the detail "Joins need Git 2.43 or later. Installed: git version 2.42.0." for Git 2.42.0. Git 2.39 and 2.40 reject `--attr-source` as an unknown option. Git 2.41 and 2.42 accept it, but `merge-tree` then ends with a segmentation fault (exit code 139) on a content merge.

| Purpose | Name |
| --- | --- |
| Task checkout | `<project>/.worktrees/<run>/<task>` |
| Task branch | `refs/heads/idp/<run>/task/<task>` |
| Join branch | `refs/heads/idp/<run>/join/<task>` |
| Result retention | `refs/idp/<run>/result/<task>/<attempt>` |
| Salvage retention | `refs/idp/<run>/salvage/<task>/<attempt>` |
| Later salvage of the same attempt | `refs/idp/<run>/resalvage/<task>/<attempt>/<operation>` |
| Approved base retention | `refs/idp/<run>/base` |

`Prepare` appends `/.worktrees/`, `/.idp/inputs/`, and `/.idp/outbox/` to the common `info/exclude`. It creates the checkout with `worktree add -b`, always as a full checkout, and locks it with an ownership reason. A failed creation that left the branch is adopted only when the creation intent, the live tip, and the registration agree. It initializes submodules only when `submodule status --recursive` shows no `+` or `U` entry, so the update never moves a module that holds commits. A continuation turn keeps its checkout and changes. Cleanup and branch deletion are deferred.

### Publication moves the branch, the index, and the result ref

`Publish` requires a logged successful closure, the task lock, and process-tree quiescence from `IExecutionBoundary`. It checks registration, symbolic HEAD, and every run ref against `RefOwnership`. The branch tip must contain the attempt base. It captures tracked edits and nonignored additions through a temporary index, excluding execution data and nested worktrees. It freezes the `.idp/outbox` manifest and the report, and journals a commit recipe whose parent is the verified tip. Then it moves the task branch by compare-and-swap, aligns the real index to the result tree without touching working files, and creates the result ref from absent. It rechecks refs, files, index, HEAD, and quiescence before it records `ResultAccepted`.

### Git reads real commit parents

Every Git process that iDevelop starts directly sets `GIT_NO_REPLACE_OBJECTS=1`, points `GIT_GRAFT_FILE` at the null device, and passes `-c core.commitGraph=false`. Without them, a writer can run `git replace --graft`, write `info/grafts`, or edit a parent in a commit-graph file so that Git reports the attempt base as an ancestor of a commit that does not contain it. Publication would then accept a result outside its attempt base. A forged commit-graph works from the repository's own graph, a split graph chain, or an alternate object store. Git prints a deprecation hint on stderr whenever it reads a graft file, even an empty one, so each process also passes `-c advice.graftFileDeprecated=false`.

### Capture ignores the writer's stat cache

Every Git process that iDevelop starts directly also passes `-c core.fsmonitor=false -c core.checkStat=default -c core.trustctime=true`. Capture runs `git add --all` against a copy of the index, and Git skips any file that its stat cache reports as unchanged. Without these settings, a writer can configure a `core.fsmonitor` hook that reports no changes, and capture leaves every edit out. Publication then accepts a result without the edit, or moves the branch and then blocks, and salvage retains a commit without it. A writer can also set `core.checkStat=minimal` and `core.trustctime=false` and restore a file's modification time after a same-size edit. With the forced settings, Git compares the full stat data, including the inode change time. A writer on Linux cannot set that time. The settings alone do not cover a same-second edit. Git compares these times in whole seconds, and it trusts an entry's stat data only when the entry is older than the index file. When the writer's own Git writes the index, it rechecks newer entries but skips those its fsmonitor hook marked valid. Suppose the writer rewrites a file with same-size content in the second its entry was refreshed, and the writer's index is next written in a later second. A copy that keeps the writer index's modification time makes the stale entry look current, and capture keeps the old blob. No index time closes this. Git treats an entry as racy only when the entry's recorded modification second is at or after the index's, and a zero index time turns the check off. An entry recorded with modification time 0, which reproducible-build tools set, is never racy, so a same-size rewrite in the same inode change second, with the time restored to 0, also kept the old blob. Capture and `GitTree.Snapshot` therefore re-add every entry that the capture considers through `git ls-files --stage | git update-index --index-info`. That keeps each entry's mode, object ID, and stage and sets its stat data to zero, so the inode and inode change time never match and `git add` hashes every included file. Entries in excluded paths stay as copied, so an intent-to-add entry there stays out of the tree. Capture and `GitTree.Snapshot` share this sequence and the adapter's Git runner. Every Git process also passes `-c core.ignoreStat=false`. With `core.ignoreStat=true`, `update-index --index-info` marks every rebuilt entry assume-unchanged after the flag check has passed, and `git add` keeps the old blob. `ls-files` runs with `--full-name`, because `--index-info` reads repository-relative names and `GitTree.Snapshot` can run from a subfolder. Capture refuses an index with an assume-unchanged or skip-worktree entry. `GitTree.Snapshot` takes the work tree's content under those entries and refuses only a skip-worktree file that is missing from the work tree, so a single-task run in a sparse checkout records no snapshot. Without that refusal, a non-sparse `git add` records every file outside the cone as deleted, and a sparse-aware one records an intent-to-add file outside the cone as empty. When iDevelop could not record or read a subject's change, its review asks the person to run the subject again in a Git project and, in a sparse checkout, to check out every file first. When a Git call times out, the runner stops Git's process tree, waits for Git to exit, and waits for its pipes to close. A process that outlived Git, such as one a hook started, can hold the pipes open, and on Linux and macOS no tree kill finds it. After 2 seconds the runner cancels its reads and closes its pipe ends, so the call returns and that process gets a broken pipe on its next write. On Linux, closing the pipes would also end those reads, but on Windows it does not, so the runner cancels them. The runner writes a call's input to the raw pipe, without a buffering writer whose disposal would replace the result, so a Git that exits without reading its input keeps its error, and a timed-out call still says it timed out. The runner deletes its temporary index and lock file without failing the call, because a scanner on Windows can hold them open. A census of what can make `git add` trust a stale entry covered stat data, fsmonitor valid bits, assume-unchanged, skip-worktree, intent-to-add, `core.ignoreStat`, sparse checkout, the sparse index, the split index, and the untracked cache. After the rebuild, only `core.ignoreStat` and the sparse cases still did. `git add` does not read the untracked cache, and a split index needs no setting. The tests ran only on Linux.

### Task worktrees are always full checkouts

Rounds 4 and 5 each changed the code to support sparse checkouts in task worktrees, and each change failed the next review. The round 4 fix let a flagged index entry through when its content matched the index. The round 5 fix aligned the index with `read-tree --reset` to keep skip-worktree bits. The round 6 review measured lost work. A writer edited a file outside the cone, Git cleared the file's skip-worktree bit, and `git add --all` skipped the file because it lay outside the sparse patterns. Publication moved the branch without the edit and then blocked. Salvage left the edit out, and retry's `reset --hard` deleted it. Each fix assumed that a task worktree must keep the main checkout's cone. iDevelop creates every task worktree itself, so it does not need to.

Every Git process that the adapter starts passes `-c core.sparseCheckout=false`. With it, `worktree add` checks out every file, whatever the main checkout's setting. It copies no sparse patterns. It does copy the main checkout's `config.worktree`, so a task worktree made from a sparse checkout has `core.sparseCheckout=true` in its own config. The forced setting overrides that value in every adapter process. A writer's own Git commands read it, but with no patterns they treat the checkout as full. Capture, salvage, index alignment, and retry never apply sparse rules either, so capture never skips a file on disk because of sparse patterns. The main checkout keeps its cone. Index alignment is a plain `read-tree` again.

Sparse state that appears in a task worktree anyway blocks. Any index entry flagged assume-unchanged or skip-worktree blocks capture, publication, salvage, and retry as `DirtyWorktree`, and the detail names the path. The block changes no file, index entry, or ref. A writer that runs `git sparse-checkout set` in its own checkout therefore blocks with every file left in place.

### Salvage and retry keep every commit reachable

`Salvage` commits the captured tree with the observed HEAD as its parent. When HEAD does not contain the branch tip, the tip becomes a second parent. The first salvage ref is immutable, and a later capture gets a `resalvage` ref. Salvage records the branch tip and the real index digest. Ignored files and dirty submodules stay in place.

`ResetForRetry` requires retained salvage, quiescence, ownership, and an unchanged inventory, including the index digest over `ls-files --stage -v`. It moves the branch from the salvaged tip by compare-and-swap, reattaches HEAD after a live check, resets, and removes only the captured untracked paths whose type and content still match. It never runs an unrestricted `git clean`.

Every step journals its intent before the Git call and its observation after it, under operation IDs derived from the caller's operation. A retry with the same operation resumes at the first unobserved step and returns the same receipt. Tests crash at every probe point and assert that.

### E2b joins with merge-tree and blocks a conflict with evidence

`MergeJoins` is the real `IJoinComposer`, and `MergeJoins.Open(projectFolder, store)` is the factory that E3 calls. It runs inside `Materializer.Prepare` and `PrepareTurn`, under the repository mutation lock that they hold. It writes Git objects and journal entries, and it moves only the join branch, through `RefPublisher`.

The sources arrive ordered by full task ID. The join's parents are their distinct commits in that order, so ancestor-related parents stay and only equal commits are dropped. `MergeJoins` chains `merge-tree --write-tree -z --messages` over the parents. Between steps it writes an accumulator commit that carries the merged tree and both parents, so each step merges real ancestry and never a bare tree. Accumulators are objects only. They get no ref, no checkout, and no journal entry. A clean join needs no checkout, so the detached accumulator checkout that the design review measured belongs to the deferred resolution design. No step uses an unborn branch.

Every join and accumulator commit takes the latest committer time of its own parents. Its message carries `IDP-Run` and `IDP-Task` trailers. The join commit is therefore a function of its inputs alone. A first version used the clock, and Sol measured the cost. Git writes the accumulator's ID into conflict markers, so a retried conflict at step 2 produced different evidence, and the retry blocked as `InputUnavailable` instead of repeating its `FanInConflict` block. The same inputs now always give the same join commit, so a retry never moves the join branch off a commit that an earlier attempt used.

A join blocks as `InputUnavailable` before any Git work when one of its sources is no longer its task's current result. Without this check, a crashed join operation retried after a source republished and a fresh join ran passed the ownership check, because the fresh join was the last recorded value, and moved the join branch back to the outdated join.

A clean merge journals a `Join` plan under the join operation and publishes the join branch from its live expected value. Before it plans, `MergeJoins` checks the live join ref against `RefOwnership`. A foreign value blocks as `UncertainOwnership` and journals nothing. A recorded plan is adopted only when a fresh clean merge gives its tree and parents, and the commit rebuilt from its recipe equals the recorded commit. Correct parents alone never authorize a join.

Git exits 0 for a clean merge and 1 for a conflict. It also exits 1 for an unknown revision, with no output, so exit 1 counts as a conflict only when the output parses. A conflict blocks as `FanInConflict`. The block records every source, the failing step, the conflicted paths, the stage entries, the message records, the Git version, the fixed merge settings, and the attribute source. The raw output is stored as `evidence/<join operation>/join-step-<step>-<digest>.stdout` and `.stderr` in the run's folder. The digest is the first 12 hexadecimal characters of SHA-256 over the output and the diagnostics. If a Git upgrade changes the output between two attempts of one operation, the retry writes new files and repeats its `FanInConflict` block, instead of colliding with the immutable files of the first attempt. Git output is decoded leniently, so a clean merge that names a non-UTF-8 path succeeds, and the stored bytes stay exact. A conflict plans nothing and moves no ref, so an older join stays where it was. A retry with the same operation returns the same block, and the run records it once.

### Joins run under a merge policy that iDevelop sets

The first review round found three defects with one premise: a join ran under whatever Git configuration and attributes the project, the user, or a writer had set. A writer that set `merge.renames=false` in its own checkout changed its sibling's join, because a linked worktree writes to the shared repository config. `merge.conflictStyle=diff3` set between two attempts of one conflicted operation changed the evidence bytes, and the retry blocked as `InputUnavailable`. An untracked `merge=keep` driver in `info/attributes` turned a conflict into a clean join that dropped one side. `merge.directoryRenames` changed where an added file landed, so adoption could not reproduce a recorded join.

`GitRepository.MergeTrees` now runs `merge-tree` in a scratch bare Git directory that it creates for each call and deletes afterwards. The directory shares the project's object database through `GIT_OBJECT_DIRECTORY` and its shallow boundary through `GIT_SHALLOW_FILE`. Its own config holds only the object format. Global, system, and inherited configuration are off. The merge process gets no `GIT_` variable from iDevelop's environment or from the caller. iDevelop sets `GIT_DIR` and `GIT_COMMON_DIR` to the scratch directory, so an inherited `GIT_COMMON_DIR` cannot bring back the project's config, its `info/attributes`, or a custom merge driver that could write refs outside the journal. The command sets `core.attributesFile` to the null device, `merge.conflictStyle=merge`, `merge.renames=true`, `merge.directoryRenames=conflict`, and `merge.renormalize=false`. Attributes come only from the run base, through `--attr-source`. The run base's committed attributes therefore apply, including the built-in `union` and `binary` drivers. A custom driver that they name has no definition, so Git uses its text merge. Untracked attributes, `info/attributes`, global attributes, and attributes that a source commits do not apply. The same inputs give the same tree and the same conflict bytes under one Git version, so adoption and conflict replay no longer depend on live settings.

The scratch directory lives in `idevelop/merges` under the common Git directory and is named by the owning process ID and a GUID. A merge that is killed leaves its directory behind, so each join removes the scratch directories there before it merges. It removes only real directories with that name form. It removes nothing when `idevelop` or `merges` is a symbolic link, a junction, or another reparse point. A join that would create its scratch directory through such a link blocks as `GitFailed` with the linked path. Cleanup deletes only the entries that iDevelop creates in a scratch directory: `HEAD`, `config`, `info/attributes`, the `refs` and `info` directories, and then the directory itself. It deletes each entry without recursion and without following a link. It leaves any other entry in place, so a scratch directory with unexpected content stays. Both join callers hold the cross-process repository mutation lock, so no other join's merge is running. A failed delete does not change the join's result, and the next join tries again. The link checks and the deletes are separate path operations. A same-user process that swaps a link into one of those paths between them can still redirect a delete. That delete reaches only files named `HEAD`, `config`, or `info/attributes` and empty directories named `refs` or `info`. A Linux race probe swapped a link at a nested entry, at the scratch directory, and at `merges`. Its outside files were journals, not those names. With the earlier recursive delete, it lost outside files in 364, 24, and 9 of 1000 tries in one run, and in 549, 23, and 46 in another. With this cleanup, it lost none in 3000 tries at each place. The race was not measured on Windows.

A `merge-tree` process can outlive the app, because nothing ties Git's lifetime to its parent. The lock is then free and the next join removes the orphan's directory. That orphan does no harm, so iDevelop does not bind the child to its parent. Traced with `strace` on Git 2.43.0 and 2.55.0, `merge-tree` with the scratch environment writes only content-addressed loose objects into the project's object directory, through a temporary file and a link. It writes nothing in the scratch directory, the refs, the index, or the run files. After setup it reads the scratch directory only for `info/attributes`, which does not exist there, so after the directory is removed it finishes the same merge. A merge it finishes alone leaves at most unreferenced objects, which `git gc` prunes. When only the app was killed, the orphan's first write of its result failed with a broken pipe, and Git ended from `SIGPIPE`. That kill was measured on Linux in 16 of 16 runs on Git 2.43.0 and 2.55.0, and not on Windows. `An_orphaned_content_merge_after_scratch_cleanup_changes_no_refs_or_execution_files` does not repeat that death. It kills no process, sends the orphan's output to files, and expects exit 0. On every run it checks that an orphan that finishes after the next join writes the same tree and changes no ref or run file. The scratch directory is plain file I/O, so the policy starts no extra Git process. A conflict starts one process fewer than before, because the evidence records the fixed settings instead of reading the live config. A probe with Git 2.55 showed what isolation needs. Without `GIT_SHALLOW_FILE`, a depth-1 clone fails with "could not parse commit". Without the object format, a SHA-256 repository fails with "not something we can merge".

E2a publishes a result commit on top of each writer's own commit. A join's parents are therefore the writers' result commits, and each writer's own commit is the first parent of its result. The design note's acceptance table named the writer commits B and C as the join's parents. The tests follow the code.

### Rejected alternatives

| Alternative | Reason for rejection |
| --- | --- |
| Judge a ref by any journal entry or ancestry that could explain it | The census put every ref failure in this class. |
| Let salvage adopt a branch tip only when it descends from the old state | It broke two salvage and retry recovery tests. The publish-time check that the tip contains the attempt base closes the same hole. |
| End the writer's lease at its `AttemptClosed` event in E2a | `AttemptClosed` records no branch tip, so the fold has no exact value to fall back on. A probe failed 49 of 91 publication, ownership, and census tests, including every writer publishing its own commits. |
| Keep the main checkout's sparse patterns in task worktrees | Two fixes on that premise failed review, and the round 6 review found a writer's edit to an out-of-cone file lost. |
| Let a flagged entry through when its content matches the index | Only sparse checkouts needed it. It cost a file-type check, a mode check, and a hash for every flagged path on every capture. |
| Compare the index file's bytes | A plain `git status` rewrites stat data and blocked retry. |
| Write `HEAD` through its lock file for an atomic attach | It bypasses reftable. `update-ref --stdin` gained `symref-verify` only in Git 2.46. |
| Reset a reviewer's branch with `reset --hard` on refresh | It dropped any reviewer commit. Refresh retains the old base and moves the branch by compare-and-swap. |
| Clock time on join and accumulator commits | A retried conflict at step 2 or later produced different evidence and blocked as `InputUnavailable`. |
| A detached checkout for every join | `merge-tree` writes the merged tree without one. The resolution design needs a checkout, and resolution is deferred. |
| Run joins under the live settings and record them | A writer's settings changed its sibling's join, and an untracked merge driver dropped one side of a conflict. Recording the settings explains the result but does not make a retry reproduce it. |
| Override each merge setting with `-c` in the project repository | Neither `-c` nor an environment variable can switch off `info/attributes` or the custom merge drivers in the repository config. |
| Ignore every attribute so that joins run on Git 2.39 | The project's committed `binary` and `union` attributes would stop applying. A lockfile marked `binary` would merge as text. |
| Raise the general Git floor to the join floor | A single-input task runs no merge. Round 1 raised the floor to 2.40, and it refused every run on Apple's Git 2.39.5 without making joins work on 2.40, 2.41, or 2.42. |
| Clear only the `GIT_` variables known to change a merge | The list would have to follow every Git release. Round 1 cleared `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS` and missed `GIT_COMMON_DIR`. |
| Keep scratch directories in the system temp folder and remove those whose process has exited | A reused process ID keeps a dead owner's directory forever. Under the mutation lock, every directory in the repository's own folder has no live owner, so no process check is needed. |
| Bind `merge-tree` to the app with a Windows Job Object or a process group | An orphaned `merge-tree` writes only objects, and the app alone moves refs and writes run files. Binding would add platform code and protect nothing. E3a.4 later put every Git call, `merge-tree` included, in its own session and process group on Linux and macOS and in a job on Windows. It stops them only when a call times out, so a hook's child that outlived its parent no longer survives the timeout. The job does not kill on close, so Git still finishes when iDevelop exits during a call. |
| Read attributes from each source | Sources can disagree, and the result would depend on the merge order. The run base is shared by every source. |
| Reuse an earlier join's recipe for the same inputs | Deriving the time from the parents makes the same inputs give the same commit with less code. |
| One 60-second limit for every Git call | It would kill a large checkout or a submodule clone. Limits are 60 seconds for metadata, 1 hour for work-tree operations, and 4 hours for submodule updates. |

## Changed artifacts

- `src/IDevelop.Core/Execution/Git/GitRepository.cs` is the Git adapter.
- `src/IDevelop.Core/Execution/Runs/` adds the code records, `RunLayout`, `RefOwnership`, `RefPublisher`, and the `Materializer` partial classes for preparation, inputs, outbox, publication, salvage, retry, refresh, and inspection. `RunStore`, `RunReducer`, `RunJournal`, and `RunRecords` gain schema 2.
- `src/IDevelop.Core/Execution/GitTree.cs` runs Git through the adapter's runner and takes snapshots through the adapter's capture sequence.
- `src/IDevelop.Core/Execution/Runs/RegularFile.cs` reads file types through `statx` or `lstat`, with `lstat$INODE64` on Intel macOS.
- `tests/IDevelop.Core.Tests/Git/`, `Materialization/`, and `Runs/` test each behavior against real scratch Git.
- `.github/workflows/dotnet.yml` adds `macos-26-intel` to the CI matrix.
- E2b adds `src/IDevelop.Core/Execution/Runs/MergeJoins.cs` and `src/IDevelop.Core/Execution/Git/GitRepository.Merge.cs`, which runs `merge-tree` under the fixed merge policy and reads committer times. It tests them in `tests/IDevelop.Core.Tests/Git/MergeTreeTests.cs` and in `JoinTests.cs`, `JoinPolicyTests.cs`, `JoinRecoveryTests.cs`, and `JoinInvariantTests.cs` under `tests/IDevelop.Core.Tests/Materialization/`.

## Open issues

1. A writer's lease outlives its closure. E3 closes attempts. It must journal the quiescent branch tip at closure as an observation and end the lease there. Three measured cases show the gap. In each, a writer closes unpublished, and its commit stays reachable only through the reflog, though no iDevelop move drops it. Each case is an E3 acceptance test with the expected outcome below. Nothing in production calls `Materializer` or `CloseAttempt` yet.
   - A foreign commit lands on the closed writer's branch. Today it becomes the parent of a published result. After E3, the writer's `Publish` and a sibling's `Publish` each block as `UncertainOwnership`, record no result, and leave the foreign commit on the branch.
   - The branch is rewritten to another descendant of the attempt base. Today `Publish` accepts a result without the writer's commit. After E3, `Publish` blocks as `UncertainOwnership` and records no result.
   - The branch is reset below the attempt base, and salvage runs after closure. Today salvage's lease clause adopts the rewind, a blocked sibling then publishes, and `ResetForRetry` moves the branch. After E3, salvage returns `Retained` without adopting the rewound tip. The sibling's `Publish` stays blocked as `UncertainOwnership`, and `ResetForRetry` blocks as `UncertainOwnership` and moves no ref.
2. Live checks protect only against iDevelop's own actors. Worktree adoption, HEAD attach, `reset --hard`, path removal, and submodule update have no compare-and-swap. They run under the task lock and the repository mutation lock, right after a live check. A process outside iDevelop that writes to the repository between the check and the Git call can still change what the call acts on. E3 must keep that window under exclusive ownership through process-tree quiescence, and must not claim protection from external writers.
3. Joins use only Git's built-in merge drivers. A custom driver named in the run base's attributes falls back to the text merge. In a partial clone, the isolated merge has no promisor remote, so a blob that was never fetched blocks the join as `GitFailed`.
4. Production `Publish` blocks as `LiveWriter` until E3 supplies process-tree evidence through `IExecutionBoundary`.
5. Read-only and review results forward code but not artifacts, so a writer's artifacts reach only its direct dependents. Forwarding artifacts needs a rule for name collisions across several dependencies.
6. Windows real-machine probes of long paths with long-path support disabled, open handles, and Job Object termination did not run beyond CI. The link checks on the scratch folders and the orphaned `merge-tree` ran only on Linux. Windows junctions are covered by the reparse-point check but not by a test. Git 2.39.5 to 2.43.0 ran only as Linux builds from source. The merge policy was measured with Git 2.43 and 2.55. No real coding-agent client ran. E2b ran only on Linux, after the user disabled GitHub Actions, so its joins have no Windows or macOS run.
7. Rebase, cleanup, resolution approval, recovered-code acceptance, and the preapproval intent file remain deferred, with their D0 requirements.
8. Every task worktree checks out every file. In a large monorepo that people keep sparse, each task pays the disk space and checkout time of the whole tree. Support for sparse task worktrees needs its own design, with a capture that cannot skip a file the writer touched.
9. iDevelop's Git processes force `core.ignoreStat=false`, so a task worktree that iDevelop checks out starts without the assume-unchanged flag. In a repository with `core.ignoreStat=true`, the writer's own `git add` still sets the flag on each entry it adds, and the task then blocks as `DirtyWorktree`.
10. Capture compares the content of every tracked file, because it sets every included entry's stat data to zero in the temporary index. It was measured on Linux with Git 2.55 and a warm page cache, as the median of 5 interleaved runs. In a generated repository of 50,000 tracked files and 210 MiB, a capture takes 452 ms (450 to 454) and opens all 50,000 files. The epoch-plus-one time it replaced took 437 ms (434 to 440), and checking only changed entries took 48 ms when measured earlier. The 15 ms difference is `ls-files` and `update-index --index-info` over 50,000 entries, and `git add` takes 400 ms in both. This repository's 536 files take 27 ms against 26 ms. The time is one core hashing. Round 7's shared sequence measured 454 ms (453 to 456) against the round 6 sequence's 452 ms (451 to 453), alternating, 5 runs each. A turn takes two captures, and `GitTree.Snapshot` costs the same for single-task runs. Stripping the fsmonitor extension from the copy and keeping the writer index's time does not fix the same-second race. Both Git processes already run with `core.fsmonitor=false`, so Git ignores the extension. The stale stat data sits in the writer's entry, and a writer index written a second later makes that entry look current. With that variant, the second-boundary test failed 3 of 3 runs, and a plain-Git stress kept the old content in 400 of 400 runs. The epoch-plus-one time fixed that race but not an entry recorded with modification time 0. In a plain-Git stress of that case, it kept the old content in 400 of 400 runs, and invalidated stat data captured the edit in 400 of 400. A cheaper check that is still correct would need to know when each entry's stat data was recorded, and the index does not store that.
