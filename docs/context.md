# iDevelop project context

## Purpose

Build a graphical interface for coordinating multiple coding agents, including Codex, Pi, Claude Code, and Antigravity CLI. Shared project records should let agents continue each other's work. The product should eventually support generating a usable multi-model configuration from a natural-language request and manually editing it afterward.

On 2026-10-18 the owner stated the goal in their own words: a node is an abstraction of an agent. It contains the model and effort it chooses, the system prompt, the instructions and skills equipped with it, the conversation with a person, the input it can read from a previous agent or a person, and the output for later agents and the person. The overall goal is a visual node and graph system that executes a task in a multi-agent environment, because each model has its advantage in some domain ([ADR 0031](adr/0031-a-node-is-an-abstraction-of-an-agent.md))

## Current scope

The repository contains the development environment, product research, and the C# desktop app on Avalonia 11.3.22 and NodifyAvalonia 6.6.0. The app keeps several project folders open, each with several workflows. It edits nodes and typed connections on a node canvas and saves each workflow to `.idp/workflows/<workflow-id>.json` inside its folder without a server. It looks like PlanWeave's desktop app in a light theme and a dark theme. Each node names its agent client, model, and reasoning setting for Claude Code, Codex, Pi, or Antigravity CLI. A person talks to a node's agent in a conversation view with Markdown, opened from the inspector or the node's card. Each node kind has its own color and glyph, one Add popover adds every node, cards and connections have context menus, the inspector follows Godot's, Generate Workflow drafts a workflow from a description, and undo covers every workflow edit. Workflow execution is Execution v2: an in-process engine starts every ready node and routes each result along its edges, and each node keeps its own log ([ADR 0042](adr/0042-execution-v2-a-node-is-an-agent-and-the-engine-only-routes-results.md)). Map issue [#179](https://github.com/Mano-Liaoyan/iDevelop/issues/179) tracks it. Team storage and the synchronization protocol remain open.

## Confirmed product direction

- The primary interface is a Miro or Unreal Blueprint-style node canvas, not a kanban board. AI generates a draft workflow that users can edit, including task relationships, agent, model, and supported reasoning settings.
- Users review generated workflows before execution.
- Both standalone solo mode and real-time team collaboration are first-release requirements. Solo mode needs no server installation or connection.
- Team mode uses an optional self-hosted synchronization service. All coding agents run on members' local machines. The service shares workflow state and does not execute agents.
- Multiple projects, workflow hierarchy navigation, dependency blocking, GitHub issues and pull-request review, and portable Markdown session records belong to the intended product.
- Provider integrations should use subscriptions or coding plans where supported, with API access also available. Provider policy and protocol compatibility must be assessed separately.
- Windows, macOS, and Linux are required. The user prefers a responsive modern UI without a JavaScript or TypeScript application stack.
- Use C# and Avalonia. The user is familiar with both and explicitly declined further framework comparisons. Use BAndysc's `NodifyAvalonia` as the starting node-editor component. Keep the local runner and optional synchronization service in C# and .NET.
- Prefer permissive dependencies such as MIT, Apache-2.0, and BSD for commercial distribution and company use without mandatory framework fees. Preserve the option of a proprietary product. No product license has been chosen.
- The interface must look like PlanWeave's desktop app: a sidebar with a project tree, rounded task cards, and floating canvas controls, in a light theme and a dark theme the user can switch between. It stays in Avalonia and NodifyAvalonia. The [product direction](product-direction.md#the-interface-follows-the-planweave-look) records the reference screenshot and what to adopt.
- The node editor works like n8n, Unreal Engine Blueprints, and Godot, with a UI in Apple's design style. Cards carry little text and vivid colors from Apple's palette, each node type and menu action has its own glyph, and states and roles have their own colors. The canvas menu adds every node type, the inspector borrows from Godot's, and a button generates a whole workflow from a description. The user asked for these on 2026-10-05, and the [product direction](product-direction.md#the-node-editor-follows-apples-design) lists them.
- On 2026-10-06 the user requested Run Workflow, automatic successor execution with predecessor content, multiple open projects with multiple workflows, an aligned Godot-inspired inspector with field icons, expandable node controls and attention requests, and a full Markdown conversation view with history. New and generated cards default to collapsed, and workflow tree rows initially hide their nodes. GitHub issue and PR creation requires an inspector action and confirmation, with results linked on the card. The [D0 record](handoffs/2026-10-06-d0-design-validation.md) holds the chosen inspector, card, and conversation layouts. The client capability probe ran on 2026-10-06 with the user's approval, and the record lists what each client supports for streaming, questions, permission requests, mid-turn input, stopping, resuming, and cancelling. C1 chose its own renderer on Markdig and Codex's app-server mode, as the [conversation record](handoffs/2026-10-07-conversation.md) records.
- Nodes have types, such as implement, plan, architect, and review. Users define their own node types without code and save any node as a blueprint. Built-in blueprints are read-only. Placing a node copies its blueprint version. Blueprints live in a personal library and in the project's `.idp/blueprints/`. A node works with the person's own commands and skills. A review is a back-and-forth between the implementer and the reviewer until both agree: the implementer continues its session with the findings, and the reviewer reviews each new result in a fresh session. After its round limit, 3 by default, the reviewer waits for the person's guidance ([ADR 0040](adr/0040-after-three-review-rounds-the-reviewer-waits-for-the-person.md)). The user can answer and redirect an agent that asks. The user confirmed these on 2026-10-04, and the [product direction](product-direction.md#nodes-have-types-that-users-define) lists them.

The [product direction](product-direction.md) records the selected stack, proposed runtime design, and acceptance cases. Framework selection is settled. Runtime design details remain provisional.

## Working decisions

- The project's working language is English, as defined in `AGENTS.md`.
- Development uses Matt Pocock's skills, the `mattpocock-skills` Claude Code plugin enabled in `.claude/settings.json`, with GitHub Issues as the tracker. [`docs/development-environment.md`](development-environment.md) describes the setup, and `docs/agents/` holds the skills' tracker, label, and domain-doc settings. New architecture decisions go to `docs/adr/` and settled vocabulary to `GLOSSARY.md`.
- The project-owned skill `.claude/skills/verify-idevelop` drives the built app's real window on Windows through `scripts/real-window.psm1`, the module `scripts/check-real-window.ps1` also uses. Its task runs go through a fake Codex, and a real client runs only when a change touches a client integration or the user asks, because a real run spends subscription quota.
- Concurrent code writers use separate worktrees. Durable decisions belong in this file, the product direction, the ADRs, and the handoff records these files link. Git history keeps everything else. Private chat transcripts never become records.
- An immutable `Workflow` value holds tasks, connections, and layout in separate collections. One pure `Workflow.Apply` owns every graph rule, and the file loader replays edits through it. A move never changes the semantic collections, so a node's basis ignores layout. Save overwrites the workflow file without checking it for changes on disk since it was loaded.
- Connections are dependency and context. Dependencies are acyclic, and context connections may form cycles. A review is a node, as the [node model](handoffs/2026-10-04-node-model.md#review-is-a-node-and-connections-express-flow) records. Opening a format 2 file turns each of its review connections into a dependency.
- Central package management and committed lock files pin every package. `scripts/check-licenses.mjs` fails on a license outside MIT, Apache-2.0, BSD-2-Clause, and BSD-3-Clause, and on a bundled notice file without a reviewed entry.
- The SkiaSharp and HarfBuzzSharp native packages that Avalonia renders through ship one third-party notice. It names terms outside the permissive list, including Skia's GIF decoder under MPL-1.1, GPL-2.0, or LGPL-2.1. Distributing a build needs a license decision on those terms.
- `Avalonia.BuildServices` sends anonymous build telemetry. The release workflow sets `AVALONIA_TELEMETRY_OPTOUT=1`, and the README explains the local opt-out.
- `Application.RequestedThemeVariant` is the only runtime theme state, so no view model holds a copy of it. The app writes `iDevelop/settings.json`, `{"theme":"system"|"light"|"dark"}`, in the per-user application data folder only when the user picks a theme.
- The app's own colors come from `src/IDevelop.Desktop/Theme/Tokens.axaml`, which `scripts/planweave-tokens.mjs` generates. Surfaces, text, and borders come from PlanWeave's color tokens, and the accent, the node kinds, and the states come from Apple's system colors. Text stays neutral except destructive menu text and links. Its `--check` mode fails on a stale file, on a listed color pair below its WCAG contrast minimum in either theme, and on the color forms the README lists elsewhere in the desktop project's XAML and C# files. It does not catch every way to make a color.
- Every icon is a Fluent UI System Icon, MIT licensed, pinned in `scripts/icons/fluent-icons.json`. `scripts/fluent-icons.mjs` generates `Theme/FluentIcons.axaml`, and its `--check` mode fails on a stale file or an icon key the app uses without a manifest entry. `THIRD-PARTY-NOTICES.md` holds the license, and the build copies it beside the app. A `PathIcon` draws through the `Glyph` theme, which keeps each icon's 16 unit frame. The [redesign record](handoffs/2026-10-05-node-system-redesign.md#decisions) gives the reasons and the rejected icon sets.
- A node's kind comes from its blueprint's built-in id, then from its `DerivedFrom` chain, then from its work. Implement is indigo, Plan cyan, Architect purple, Review mint, Approval brown, Merge pink, and a read-only agent gray, each with its own glyph in a tile. A card is 240 by 64 and shows the tile, the title, and two lines under it: the client, or the status while the task has one, and then the model and level in every state, so no agent name is cut short. A card's chevron expands it in place to 320 px, with what goes on now, its agent's pickers, and its actions, while its neighbours slide aside on screen only and the workflow keeps its positions. A collapsed card's tooltip is a read-only peek, and the window remembers each workflow's expanded cards on this machine ([ADR 0024](adr/0024-an-expanded-card-unfolds-in-place-and-stays-expanded-on-this-machine.md)). Its state shows in its ring, a tint, and a glyph, and a planner with an open proposal takes the Proposing role. A connection takes its source kind's color. A dependency is solid, and a context connection is dashed.
- One Add popover adds every node, from a right-click, a double-click, or N on empty canvas, the sidebar's Add Node button, a wire dropped on empty canvas, and Insert Node on a connection. A node added from a wire or an insert joins its connections in the same edit. Cards and connections have context menus, and the canvas reads its own keys in a handled `KeyDown`, because NodifyAvalonia's key gestures never fire.
- The inspector follows Godot's: a pinned header, a property filter, foldable sections, two-column rows, and revert arrows. With nothing selected, it shows the workflow's kinds and the blueprint library, where the person manages blueprints. Every inspector view shares one column grid, `InspectorGrid`, so buttons and glyphs end 12 px from the panel's edge, and boxes and paragraphs 64 px. The overview's counts end where the glyphs' drawing ends, the label column keeps one width, every row centres on a 28 px first line, a label over its value sits on a 24 px line, text wraps instead of ending in an ellipsis, and below 440 px, which includes the 320 px default, every value sits under its label so the longest model names fit ([ADR 0021](adr/0021-the-inspector-keeps-two-right-edges-and-stacks-values-below-440-px.md)).
- The canvas keeps 336 px beside the sidebar and the inspector, and 280 px of height above the docked conversation while the conversation keeps its header, its composer, and a few lines of transcript. Below 640 px it is compact: its buttons show only their glyphs, the breadcrumb only the workflow's name, and the minimap hides. Its top row keeps the breadcrumb, the waiting pill, Run Workflow, and Generate apart, with the pill under the buttons when the row has no room for it. Its bottom row keeps the zoom controls, the bar, and the minimap on the bottom edge. The conversation view's rows move their controls under their text ([ADR 0023](adr/0023-the-canvas-keeps-336-px-and-its-controls-follow-its-own-size.md)).
- Generate Workflow is design time. It places a built-in Plan node in Chat mode with the person's description as its goal and runs it. Its proposal lands as ghost cards, and nothing joins the workflow before Accept. The person can edit the workflow at any time ([ADR 0042](adr/0042-execution-v2-a-node-is-an-agent-and-the-engine-only-routes-results.md)). A planner reads the clients that are ready on the machine, with their models and reasoning levels, and proposes a client, a model, a level, and a one-line reason for each node it adds whose blueprint has no agent of its own, since a blueprint's saved agent wins, and for each node it fills that has no agent. Each ghost card and review row shows the node's agent on a card's two lines, and the person can change it before accepting. A fill keeps the agent its node has, and its row says "Set on the task". A choice the machine cannot run falls back, with a note in a tab under its ghost card and on its row. A box in the Proposal section, on only for a planner that Generate placed, gives the planner's agent to a new node, or a fill, that has no agent of its own and no usable choice. The user confirmed that box on 2026-10-06 and asked for per-task agents on 2026-10-09 in issue [#91](https://github.com/Mano-Liaoyan/iDevelop/issues/91). [ADR 0019](adr/0019-a-planner-chooses-each-new-task-s-agent.md) records the decision.
- `WorkflowDocument` keeps undo and redo. Each applied edit is one step, typing in one field or title folds into one step, and undoing back to the saved workflow reads as saved. The window runs Ctrl+Z, Ctrl+Shift+Z, and Ctrl+Y after the focused control, so a text box keeps its own undo.
- A node is an agent whose output, a report plus an optional commit, depends only on its basis: its inputs, the latest results of its predecessors, its instruction, and its model. The engine starts every ready node at once, a node whose predecessors are all completed and not stale, and on completion sends its result along every outgoing edge ([ADR 0018](adr/0018-every-ready-node-starts-at-once.md)). `CliAgent` runs a coding client, and `PersonAgent` approves or sends back ([ADR 0007](adr/0007-a-person-agent-approves-or-sends-back.md)). Review and Merge are blueprints that `CliAgent` runs. A result is stale when its recorded basis differs from the current one. An upstream rerun stops a running node after it and runs it again in a fresh session once the upstream completes, and a person's edit of a running node stops it and waits for the person's Run ([ADR 0034](adr/0034-a-result-goes-stale-when-its-basis-changes.md)). Each editing node works in its own Git worktree on its own branch, `idp/<workflow>/<node>`, and each turn ends with one commit. A node's worktree starts from the merge of its predecessors' commits, and a root node's from the HEAD of the project's branch. A read-only node, such as Review, runs in the project folder without a worktree and commits nothing. A Retry starts a fresh session in a clean worktree ([ADR 0032](adr/0032-each-editing-node-works-in-its-own-worktree.md)). A conflict between predecessors goes to the Merge node they connect into, or the node waits for the person to resolve it in its worktree and mark it resolved. Merge into my branch is offered only when every node is completed and nothing is stale, and merges every end node's commit into the checked-out branch ([ADR 0033](adr/0033-a-merge-node-resolves-conflicts-and-merge-into-my-branch-waits-for-a-complete-workflow.md)). A review after a Merge node reviews the merge ([ADR 0037](adr/0037-a-review-after-a-merge-node-reviews-the-merge.md)). A review's reject and an approval's send back go along a feedback edge to the direct predecessors, which continue in their own session and worktree ([ADR 0041](adr/0041-feedback-goes-to-the-direct-predecessor.md), [ADR 0035](adr/0035-send-back-is-a-feedback-edge.md)), and after a node's round limit, 3 by default, the reviewer waits for the person ([ADR 0040](adr/0040-after-three-review-rounds-the-reviewer-waits-for-the-person.md)). A review's verdict lists findings, each with a severity and a location ([ADR 0029](adr/0029-a-finding-has-a-severity-and-a-location.md)).
- Each client runs one process per turn with a JSON event stream, as the [agent client behavior](agent-clients.md) reference records. Claude Code streams JSON in both directions, Codex runs `codex app-server`, and Pi and Antigravity CLI read the prompt from stdin. The client's own event stream decides success, because Pi exits with code 0 after a failed turn. Each node keeps one append-only log of its results and its session id, which the engine replays when the project opens. Git ignores it.
- An attempt is one fresh session of a node's agent and holds one or more turns. A turn is one client process, and the turns share the client's own session, so no process runs between them. A message the person sends while a turn runs waits for that turn to end. For Claude Code and Codex, Stop and send first sends the client's own interrupt, reads until the turn's final result, and then stops the turn's process tree. For Pi and Antigravity CLI, it stops the process tree at once. Then the next turn resumes the session with the message alone. A message to a node that is not running is the next turn of its session. No client process waits between messages, and the conversation view reads the turns of one session as one conversation. Pi finds a session only in the folder where it ran, so a message to a Pi conversation whose project folder moved since the session started is refused with a note that a new conversation is needed, and its Open in terminal is off ([ADR 0026](adr/0026-a-continued-session-reads-as-one-conversation.md)). Open in terminal copies the client's own command for the session, after a change into the project folder, and records the hand-off in the node's log. A turn that was running when the app closed reopens as input-required, and the person chooses Continue or Retry. The [node model record](handoffs/2026-10-04-node-model.md#interaction-resumes-the-clients-own-session) holds the design.
- The workflow file format is `idevelop.workflow/3`. It embeds one copy of each blueprint version its nodes use, and each task stores its blueprint key, field values, `execution` (client, model, and reasoning), and conversation mode. The app writes only version 3. It reads version 2 and converts each task to a node of the built-in Implement, and the format 2 reader goes once no format 2 file remains. A workflow may carry an optional `name`, and a blueprint an optional `icon` and `color` from closed lists, with no format bump. An older build refuses a file that uses them. The [workspace record](handoffs/2026-10-07-workspace-sessions.md) gives the reasons.
- A node's conversation mode is Autonomous, May ask, or Chat. A node that waits for the person after its turn ends holds no process, and the person's reply is the next turn of its session. The [node model record](handoffs/2026-10-04-node-model.md#interaction-resumes-the-clients-own-session) describes the modes. Claude Code in a May ask or Chat node asks on its own channel: its turn stays alive, the node is input-required with the question and its choices, and `WorkflowEngine.Answer` sends the person's answer back into that turn under a key the engine owns. The node log records each question and answer, and a question still waiting when the app closes reopens as an interrupted turn. Codex, Pi, and Antigravity CLI ask in their reply, and the person's next message resumes the session. Permission requests are declined, except that Claude Code in an editing node runs with `bypassPermissions` and asks for none ([ADR 0039](adr/0039-claude-code-in-an-editing-node-runs-with-bypass-permissions.md)). The [conversation record](handoffs/2026-10-07-conversation.md) holds the policy.
- One window keeps several projects open, and a project opens in one window only: a lock file keeps it there, and a second window shows that the project is already open in another window. Switching a project or workflow stops nothing. The window remembers its open projects in `session.json` beside `settings.json`.
- GitHub Actions runs `.github/workflows/dotnet.yml` on Windows and macOS for a `v*` release tag or when started by hand. Each pull request passes the local checks that `AGENTS.md` lists. Pull request [#43](https://github.com/Mano-Liaoyan/iDevelop/pull/43), which makes CI fail fast, waits for the user's decision on CI.
- The app finds clients on PATH, plus the current machine and user PATH from the registry on Windows and the login shell's PATH on macOS and Linux. It reads them again at each refresh of the AGENTS section. Each client's own commands decide its readiness and its models. Claude Code has no model list command, so iDevelop carries its model list.
- A node's agent uses every skill its client loads until the person chooses some in the inspector's Skills row. The row lists the skills that the node's client loads in the project, as the client lists them without a model turn, its built-in skills included where the listing tells them apart. Claude Code and Pi then get exactly the chosen skills, and Codex turns off the others. Antigravity CLI can't limit its skills per task, so its picker is off and says so. A chosen skill that is no longer installed is skipped with a note, and the task still runs. When the client's skill list can't be read at launch, the task still runs, and a note says so: Claude Code gets the chosen names unchecked, and for Codex and Pi, which need the list to limit their skills, the choice can't be applied and they run with all of them. The owner decided this on 2026-10-09 and 2026-10-11 in issue [#93](https://github.com/Mano-Liaoyan/iDevelop/issues/93) ([ADR 0025](adr/0025-a-node-s-skill-choice-is-exactly-its-skills-and-each-client-gets-it-its-own-way.md)).
- A node's agent may edit files in its worktree. Commands follow each client's non-interactive rules. Claude Code denies commands it has not been allowed, Codex runs them in its workspace sandbox, Antigravity CLI blocks them, and Pi has no permission system. Every Codex turn passes `-c approval_policy=never`, because a user's approval policy can let Codex's automatic reviewer approve a command outside the sandbox. On Windows each client runs in a Job Object, so Stop, leaving the project, or closing iDevelop while a node runs stops every process the client started. A turn stops what its client left running once the client exits, through the Job Object on Windows and the process group the turn leads on Linux and macOS ([ADR 0001](adr/0001-unix-workflow-turns-lead-their-own-session.md)).
- iDevelop works around these NodifyAvalonia 6.6.0 defects, so a Nodify upgrade should retest each one. Connections draw over the cards. The minimap does not follow a moved task, and its wheel zooms about 0.2% per notch. The animated pan does not update the bound viewport location. Connections never raise the context menu request. Commands on buttons outside the editor never reach it. The editor's key gestures, including Ctrl+A, still do not fire. Each decorator, such as a proposal's ghost card, keeps its size at every zoom.
