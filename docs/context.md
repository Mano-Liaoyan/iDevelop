# iDevelop project context

## Purpose

Build a graphical interface for coordinating multiple coding agents, including Codex, Pi, Claude Code, and Antigravity CLI. Shared project records should let agents continue each other's work. The product should eventually support generating a usable multi-model configuration from a natural-language request and manually editing it afterward.

## Current scope

The repository contains the development environment, product research, and the C# desktop app on Avalonia 11.3.22 and NodifyAvalonia 6.6.0. The app keeps several project folders open, each with several workflows. It edits tasks and typed connections on a node canvas and saves each workflow to `.idp/workflows/<workflow-id>.json` inside its folder without a server. It looks like PlanWeave's desktop app in a light theme and a dark theme. Each task names its agent client, model, and reasoning setting for Claude Code, Codex, Pi, or Antigravity CLI. A node's Run starts a workflow run of that node, and Generate Workflow's planner runs on its own in the project folder. A person talks to a task's agent in a conversation view with Markdown, opened from the inspector or the task's card. Each node kind has its own color and glyph, one Add popover adds every node, cards and connections have context menus, the inspector follows Godot's, Generate Workflow drafts a workflow from a description, and undo covers every workflow edit. Core holds run records, dependency-result materialization, and a workflow run coordinator. Run Workflow checks the whole workflow in a preflight, starts the approved run, and shows its status, its tasks' conversations, and its approvals. Its tasks' inspectors preserve and restore a changed checkout, close a turn that a crash left unresolved, rebase a stale result, and continue or retry an interrupted review fix. Team storage and the synchronization protocol remain open.

## Confirmed product direction

- The primary interface is a Miro or Unreal Blueprint-style node canvas, not a kanban board. AI generates a draft workflow that users can edit, including task relationships, agent, model, and supported reasoning settings.
- Users review generated workflows before execution.
- Both standalone solo mode and real-time team collaboration are first-release requirements. Solo mode needs no server installation or connection.
- Team mode uses an optional self-hosted synchronization service. All coding agents run on members' local machines. The service shares workflow state and does not execute agents.
- Multiple projects, workflow hierarchy navigation, dependency blocking, GitHub issues and pull-request review, and portable Markdown session records belong to the intended product.
- Provider integrations should use subscriptions or coding plans where supported, with API access also available. Provider policy and protocol compatibility must be assessed separately.
- Windows, macOS, and Linux are required. The user prefers a responsive modern UI without a JavaScript or TypeScript application stack.
- Use C# and Avalonia. The user is familiar with both and explicitly declined further framework comparisons. Use BAndysc's `NodifyAvalonia` as the starting node-editor component. Keep the local runner and optional synchronization service in C# and .NET.
- Prefer permissive dependencies such as MIT, Apache-2.0, and BSD for commercial distribution and company use without mandatory framework fees. Preserve the option of a proprietary product. No product license has been chosen.
- The interface must look like PlanWeave's desktop app: a sidebar with a project tree, rounded task cards, and floating canvas controls, in a light theme and a dark theme the user can switch between. It stays in Avalonia and NodifyAvalonia. The [product direction](product-direction.md#the-interface-follows-the-planweave-look) records the reference screenshot and what to adopt.
- The node editor works like n8n, Unreal Engine Blueprints, and Godot, with a UI in Apple's design style. Cards carry little text and vivid colors from Apple's palette, each node type and menu action has its own glyph, and states and roles have their own colors. The canvas menu adds every node type, the inspector borrows from Godot's, and a button generates a whole workflow from a description. The user asked for these on 2026-10-05, and the [product direction](product-direction.md#the-node-editor-follows-apples-design) lists them.
- On 2026-10-06 the user requested Run Workflow, automatic successor execution with predecessor content, multiple open projects with multiple workflows, an aligned Godot-inspired inspector with field icons, expandable node controls and attention requests, and a full Markdown conversation view with history. New and generated cards default to collapsed, and workflow tree rows initially hide their nodes. GitHub issue and PR creation requires an inspector action and confirmation, with results linked on the card. The [workspace and execution plan](handoffs/2026-10-06-workspace-execution-plan.md) records the requirements, delivery slices, and verification coverage. The user approved the plan on 2026-10-06 and authorized D0 later that day. The [D0 record](handoffs/2026-10-06-d0-design-validation.md) holds the Git contract for E2 and the chosen inspector, card, and conversation layouts. The client capability probe ran on 2026-10-06 with the user's approval, and the record lists what each client supports for streaming, questions, permission requests, mid-turn input, stopping, resuming, and cancelling. C1 chose its own renderer on Markdig and moved Codex to its app-server mode, as the [conversation record](handoffs/2026-10-07-conversation.md) records.
- Nodes have types, such as implement, plan, architect, and review. Users define their own node types without code and save any node as a blueprint. Built-in blueprints are read-only. Placing a node copies its blueprint version. Blueprints live in a personal library and in the project's `.idp/blueprints/`. iDevelop depends on no skill library such as PStack. A review is a back-and-forth between the implementer and the reviewer, each in its own continuing session, until both agree, with no round limit. The user can answer and redirect an agent that asks. The user confirmed these on 2026-10-04, and the [product direction](product-direction.md#nodes-have-types-that-users-define) lists them.

The [product direction](product-direction.md) records the selected stack, proposed runtime design, and acceptance cases. Framework selection is settled. Runtime design details remain provisional.

## Working decisions

- The project's working language is English, as defined in `AGENTS.md`.
- Development uses Matt Pocock's skills, the `mattpocock-skills` Claude Code plugin enabled in `.claude/settings.json`, with GitHub Issues as the tracker. The user replaced PStack and its per-role model policy with them on 2026-10-08 because the multi-model review rounds cost too much time and too many tokens. [`docs/development-environment.md`](development-environment.md) describes the setup, and `docs/agents/` holds the skills' tracker, label, and domain-doc settings. New architecture decisions go to `docs/adr/` and settled vocabulary to `GLOSSARY.md`.
- The project-owned skill `.claude/skills/verify-idevelop` drives the built app's real window on Windows through `scripts/real-window.psm1`, the module `scripts/check-real-window.ps1` also uses. Its task runs go through a fake Codex, and a real client runs only when a change touches a client integration or the user asks, because a real run spends subscription quota.
- Concurrent code writers use separate worktrees. Durable decisions belong in this file, the product direction, and the few handoff records they link. Git history keeps everything else. Private chat transcripts never become records.
- An immutable `Workflow` value holds tasks, connections, and layout in separate collections. One pure `Workflow.Apply` owns every graph rule, and the file loader replays edits through it. A move never changes the semantic collections, so a later approval can ignore layout. The [canvas handoff](handoffs/2026-10-03-editable-local-canvas.md) records the design and its alternatives.
- Connections are dependency and context. Dependencies are acyclic, and context connections may form cycles. The [node model](handoffs/2026-10-04-node-model.md#review-is-a-node-and-connections-express-flow) replaced the review connection with a review node, which slice 5 built. Opening a format 2 file turns each review connection into a dependency.
- Central package management and committed lock files pin every package. `scripts/check-licenses.mjs` fails on a license outside MIT, Apache-2.0, BSD-2-Clause, and BSD-3-Clause, and on a bundled notice file without a reviewed entry.
- The SkiaSharp and HarfBuzzSharp native packages that Avalonia renders through ship one third-party notice. It names terms outside the permissive list, including Skia's GIF decoder under MPL-1.1, GPL-2.0, or LGPL-2.1. Distributing a build needs a license decision on those terms.
- `Avalonia.BuildServices` sends anonymous build telemetry. CI sets `AVALONIA_TELEMETRY_OPTOUT=1`, and the README explains the local opt-out.
- `Application.RequestedThemeVariant` is the only runtime theme state. The app writes `iDevelop/settings.json` in the per-user application data folder only when the user picks a theme. The [restyle record](handoffs/2026-10-04-planweave-restyle.md) records the design and its alternatives.
- The app's own colors come from `src/IDevelop.Desktop/Theme/Tokens.axaml`, which `scripts/planweave-tokens.mjs` generates. Surfaces, text, and borders come from PlanWeave's color tokens, and the accent, the node kinds, and the states come from Apple's system colors. Text stays neutral except destructive menu text and links. Its `--check` mode runs in CI. It fails on a stale file, on a listed color pair below its WCAG contrast minimum in either theme, and on the color forms the README lists elsewhere in the desktop project's XAML and C# files. It does not catch every way to make a color.
- Every icon is a Fluent UI System Icon, MIT licensed, pinned in `scripts/icons/fluent-icons.json`. `scripts/fluent-icons.mjs` generates `Theme/FluentIcons.axaml`, and its `--check` mode runs in CI and fails on a stale file or an icon key the app uses without a manifest entry. `THIRD-PARTY-NOTICES.md` holds the license, and the build copies it beside the app. A `PathIcon` draws through the `Glyph` theme, which keeps each icon's 16 unit frame. The [redesign record](handoffs/2026-10-05-node-system-redesign.md#decisions) gives the reasons and the rejected icon sets.
- A node's kind comes from its blueprint's built-in id, then from its `DerivedFrom` chain, then from its work. Implement is indigo, Plan cyan, Architect purple, Review mint, Approval brown, and a read-only agent gray, each with its own glyph in a tile. A card is 240 by 64 and shows the tile, the title, and two lines under it: the client, or the status while the task has one, and then the model and level in every state, so no agent name is cut short. Its state shows in its ring, a tint, and a glyph, and a planner with an open proposal takes the Proposing role. A connection takes its source kind's color. A dependency is solid, and a context connection is dashed.
- One Add popover adds every node, from a right-click, a double-click, or N on empty canvas, the sidebar's Add Node button, a wire dropped on empty canvas, and Insert Node on a connection. A node added from a wire or an insert joins its connections in the same edit. Cards and connections have context menus, and the canvas reads its own keys in a handled `KeyDown`, because NodifyAvalonia's key gestures never fire.
- The inspector follows Godot's: a pinned header, a property filter, foldable sections, two-column rows, and revert arrows. With nothing selected, it shows the workflow's kinds and the blueprint library, which replaced the palette as a place to manage blueprints. Since U1, every inspector view shares one column grid, `InspectorGrid`, so buttons and glyphs end 12 px from the panel's edge, and boxes and paragraphs 64 px. Since #88, the overview's counts end where the glyphs' drawing ends, the label column keeps one width, every row centres on a 28 px first line, a label over its value sits on a 24 px line, text wraps instead of ending in an ellipsis, and below 440 px, which includes the 320 px default, every value sits under its label so the longest model names fit ([ADR 0021](adr/0021-the-inspector-keeps-two-right-edges-and-stacks-values-below-440-px.md)).
- Generate Workflow places a built-in Plan node in Chat mode with the person's description as its goal and runs it. Its proposal lands as ghost cards, and nothing joins the workflow before Accept. A planner that the app starts reads the clients that are ready on the machine, with their models and reasoning levels, and proposes a client, a model, a level, and a one-line reason for each task it adds whose blueprint has no agent of its own, since a blueprint's saved agent wins. Each ghost card and review row shows the task's agent on a card's two lines, and the person can change it before accepting. A choice the machine cannot run falls back, with a note in a tab under its ghost card and on its row. A box in the Proposal section, on only for a planner that Generate placed, gives a new task that has no agent of its own the planner's agent when its blueprint has none. The user confirmed that box on 2026-10-06 and asked for per-task agents on 2026-10-09 in issue [#91](https://github.com/Mano-Liaoyan/iDevelop/issues/91). A run's planner still chooses no agent, because its prompt must render the same from its attempt alone. [ADR 0019](adr/0019-a-planner-chooses-each-new-task-s-agent.md) records the decision, which reverses the node model's rule that a planner never chooses agents.
- `WorkflowDocument` keeps undo and redo. Each applied edit is one step, typing in one field or title folds into one step, and undoing back to the saved workflow reads as saved. The window runs Ctrl+Z, Ctrl+Shift+Z, and Ctrl+Y after the focused control, so a text box keeps its own undo.
- A task's run edits the project folder itself. Several tasks of a project folder can run at once, and each task runs at most once at a time, across every app instance. An operating-system lock on `.idp/attempts/<task-id>/run.lock` enforces it. The user asked for parallel runs on 2026-10-04, after phase 3 first shipped with one run per folder. Git worktrees and branches wait for workflow execution, where the results of separate runs must stay apart until they are merged. The [execution record](handoffs/2026-10-04-single-task-execution.md) records the design and its alternatives.
- Each client runs one process per turn with a JSON event stream, as the [agent client behavior](agent-clients.md) reference records. Claude Code streams JSON in both directions, Codex runs `codex app-server`, and Pi and Antigravity CLI read the prompt from stdin. The client's own event stream decides success, because Pi exits with code 0 after a failed turn. Each attempt is an append-only event log at `.idp/attempts/<task-id>/<attempt-id>/events.jsonl`, which one pure reducer folds into the attempt's record. Git ignores that folder.
- An attempt holds one or more turns. A turn is one client process, and the turns share the client's own session, so no process runs between them. A message the person sends while a turn runs waits for that turn to end. For Claude Code and Codex, Stop and send first sends the client's own interrupt, reads until the turn's final result, and then stops the turn's process tree. For Pi and Antigravity CLI, it stops the process tree at once. Then the next turn resumes the session with the message alone, under the same log and lock. A cancel or leave still ends the whole attempt. A message to a task that is not running starts a new attempt whose first turn resumes the latest attempt's session, and that attempt stays as it was. Open in terminal copies the client's own command for the session, after a change into the project folder, and records the hand-off on the attempt. New attempt events carry all of this, so every earlier log folds as before. The [node model record](handoffs/2026-10-04-node-model.md#interaction-resumes-the-clients-own-session) holds the design.
- The workflow file format is `idevelop.workflow/3`. It embeds one copy of each blueprint version its nodes use, and each task stores its blueprint key, field values, `execution` (client, model, and reasoning), and conversation mode. The app writes only version 3. It reads version 2 and converts each task to a node of the built-in Implement, and the format 2 reader goes once no format 2 file remains. The user dropped version 1 on 2026-10-04. A workflow may carry an optional `name`, and a blueprint an optional `icon` and `color` from closed lists, with no format bump. An older build refuses a file that uses them. The [workspace record](handoffs/2026-10-07-workspace-sessions.md) gives the reasons.
- A node's conversation mode is Autonomous, May ask, or Chat. A node that waits for the person holds no process and no lock, and the person's reply is the next turn of the same attempt. The [node model record](handoffs/2026-10-04-node-model.md#delivery) lists what slice 2 built. A structured question is deferred at once into a text question, and the person's next message resumes the session. Permission requests are declined. The [conversation record](handoffs/2026-10-07-conversation.md) holds the policy.
- One window keeps several projects open. Each open folder has one `ProjectRuns` that follows every workflow, so switching a project or workflow stops nothing. The window remembers its open projects in `session.json` beside `settings.json`.
- The user disabled the repository's GitHub Actions workflows on 2026-10-07 until they decide how to handle CI. Each pull request passes the local checks that `AGENTS.md` lists. The checks that this file says run in CI do not run until the user enables the workflows again.
- The app finds clients on PATH, plus the current machine and user PATH from the registry on Windows and the login shell's PATH on macOS and Linux. It reads them again at each refresh of the AGENTS section. Each client's own commands decide its readiness and its models. Claude Code has no model list command, so iDevelop carries its model list. No per-user client setting exists.
- A run may edit files in the project folder. Commands follow each client's non-interactive rules. Claude Code denies commands it has not been allowed, Codex runs them in its workspace sandbox, Antigravity CLI blocks them, and Pi has no permission system. Every Codex run passes `-c approval_policy=never`, because a user's approval policy can let Codex's automatic reviewer approve a command outside the sandbox. On Windows each client runs in a Job Object, so Cancel, leaving the project, or closing iDevelop during a run stops every process the client started. A run that ends on its own leaves running what the client started on purpose, such as a dev server, on every platform. Cancel, Stop and send, and leaving stop a turn's processes only while its client still runs, so once the client has exited they leave what it started running, even while that still holds the client's output open, and Cancel still records the attempt as Cancelled.
- iDevelop works around these NodifyAvalonia 6.6.0 defects, so a Nodify upgrade should retest each one. Connections draw over the cards. The minimap does not follow a moved task, and its wheel zooms about 0.2% per notch. The animated pan does not update the bound viewport location. Connections never raise the context menu request. Commands on buttons outside the editor never reach it. The editor's key gestures, including Ctrl+A, still do not fire.

A node's run counts a current result from an earlier run as complete and carries it into the run, its code replayed onto the run's base, and a result whose code conflicts with that base means its task must run again ([ADR 0022](adr/0022-a-node-s-run-carries-the-current-results-of-earlier-runs.md)). Run Workflow carries nothing, and each card keeps its task's state between runs and after a restart: Succeeded, Out of date, or Waits for the tasks before it. Under E3e's gates, an Approval node records a durable request on its composed inputs and runs no client. The person's approval records a human-origin result that hands on the request's code, reports, and artifacts, and a send back holds the node's dependents until its inputs change. `WorkflowSchedule` returns the tasks that can start and what holds back each blocked task. A task can start when every dependency predecessor's latest attempt succeeded. A context connection never holds a task back, and a failure holds back only the tasks below it. A review holds back the tasks after it until it ends approved, and an approval until the person approves.
